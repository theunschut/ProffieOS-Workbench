<objective>
Establish the typed exception foundation for error surfacing: introduce a small `SaberProtocolException` hierarchy, make `SaberCommandService.Send2()`/`Send()` throw a distinguishable exception per failure mode (unsupported / timeout / disconnected / communication) instead of silently returning `""`, add structured `ILogger<SaberCommandService>` logging at each throw site, and — critically — migrate every existing call site in `SaberStateService.cs` that currently treats a `Whut?`-prefixed or empty string as a normal outcome, so the breaking change lands without crashing the app.

This plan delivers ERR-02's enabling mechanism (D-03/D-05): once failure reason is distinguishable at the `Send()` layer, "unsupported" vs "timed out" vs "disconnected" naturally separate. It produces no user-visible change on its own — after this plan the app connects, syncs, and loads settings byte-for-byte identically to before — but every internal failure now carries a typed reason instead of collapsing to `""`. Plan 02 (Wave 2) consumes these exception types to render the visible banner, retry, and toast.

Purpose: Without this foundation, every failure looks identical to "board doesn't support this" (the exact conflation D-03 calls out), so ERR-01/ERR-02 cannot be built. This is the breaking change STATE.md flagged as a blocker and D-05 explicitly took on as in-scope.

Output: `SaberExceptions.cs` (new), modified `SaberCommandService.cs` (throw + log + inject logger), modified `SaberStateService.cs` (all call sites migrated), plus a documented live-board verification result for the `Whut?`-classification-layer open question.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Board firmware → C# service layer | Raw response strings (including `Whut?` and any malformed/partial output) cross from the USB/BLE device into `SaberCommandService`. ## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | Typed exception `.Message` values surfaced to UI (Plan 02 banner/toast) | mitigate | Exception messages are hardcoded human-readable templates (RESEARCH.md Pattern 1) containing only the command name — no stack traces, no secrets, no internal timing/state. Full exception detail (incl. stack trace) is logged via `ILogger`; only `.Message` reaches the user. (ASVS V7) |
| T-01-02 | Tampering | Board-supplied response text written to `ILogger` in `SaberCommandService` | mitigate | All log calls use structured-logging parameters (`_logger.LogWarning("...{Command}...", cmd)`), never string-interpolation of raw board output into the log template — this is the standard log-forging mitigation. Enforced in Task 2's acceptance criteria. (ASVS V7) |
| T-01-03 | Denial of Service | `RunLoop` / settings load crashing on an unhandled `SaberProtocolException` post-migration | mitigate | Task 2 migrates every response-inspecting call site to catch the new exceptions; `RunLoop`'s per-command failures are caught to keep the loop running (matching existing "keep running" intent). A missed call site would crash the load — the exhaustive-grep acceptance criterion is the control. |
| T-01-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this plan — `Microsoft.Extensions.Logging` is transitively available via the existing Blazor WASM SDK reference; no new dependency introduced (RESEARCH.md Package Legitimacy Audit: not applicable). No slopcheck checkpoint needed. |
