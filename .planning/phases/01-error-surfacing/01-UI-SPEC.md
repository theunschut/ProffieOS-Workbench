# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Applicability note:** This project is a Blazor WebAssembly app using MudBlazor 9.1.0 — not React/Next.js/Vite. The shadcn initialization gate from the standard UI-SPEC process does not apply (`components.json` is not a relevant artifact for this stack). `Tool: none` is set accordingly, and all "registry" sections below are marked not applicable. The design system already exists in this codebase (`MainLayout.razor.cs` MudTheme + `wwwroot/css/app.css`) — this contract documents and extends it for Phase 1's three new surfaces (panel-level error banner, global toast, unsupported-vs-failed distinction) rather than inventing a new one.

| Token | Value | Usage |
|-------|-------|-------|

**Exceptions for this phase:**

- New per-item retry button inside the banner: use MudBlazor's default `MudButton` `Size.Small` padding (not a custom value) to stay inside the existing 4px-multiple system without a new token.

## Typography

Confirming existing codebase convention — no new sizes or weights introduced by this phase:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`MudText Typo="Typo.body2"` default) | 400 (regular) | 1.5 |
| Label | 12px (`.field-label`, `.setting-label` classes: 0.72–0.76rem) | 400 (regular), StarJedi family | 1.2 |
| Heading (panel title) | 11px (`.panel-topline-text`: 0.7rem, StarJedi, lowercase) | 400 (StarJedi has no distinct weight variants in use) | 1.1 (`.starjedi-title` line-height) |
| Display (page title) | 20–22px (`.wb-title`: clamp(0.9rem, 2vw, 1.25rem)) | 400, StarJedi family | 1.1 |

**Phase 1 new text elements:**
- Error banner heading/body text: `MudText Typo="Typo.body2"` (14px/400/1.5) — matches existing `MudAlert` default typography, no override needed.
- Per-setting failure reason text (inside banner list): `MudText Typo="Typo.caption"` (12px/400/1.5) — same as existing `.field-label` usage elsewhere in `SettingsPanel.razor`.
- Global Snackbar toast text: inherits MudBlazor `Snackbar` default typography — already used at 20+ call sites in this codebase, no change.

**Note on weight:** This codebase does not use bold/semibold text anywhere in the audited surfaces — StarJedi display font and Roboto body font both render at regular weight throughout. Phase 1 introduces no bold text. This deviates from the standard "2 weights" guidance only because the existing design system is genuinely single-weight; do not introduce a second weight for this phase's new banner/toast — matching the existing visual language takes precedence.

## Copywriting Contract

Per D-05, error copy carries a **specific reason**, never a generic "failed to load." Per CONTEXT.md's Claude's Discretion, exact wording is this agent's responsibility — the following is the prescriptive, final copy contract for Phase 1's three new user-facing surfaces (panel banner, global toast, retry button). All copy follows the existing codebase's lowercase, terse, StarJedi-flavored voice (see `panel-topline-text: "settings"`, `wb-title`, `.eyebrow` text) for structural chrome, but uses **sentence case for actual error messages** (matching existing `Snackbar.Add($"Failed to load settings: {ex.Message}", ...)` convention) since error text must be immediately scannable, not stylized.

| Element | Copy |
|---------|------|
| Panel banner heading | "Some settings couldn't be loaded" (`MudAlert Severity="Severity.Error"`, shown above the failed-settings list in `SettingsPanel.razor`, only when `State.FailedSettings.Count > 0`) |
| Panel banner per-item row | `{Label}: {ex.Message}` — e.g. "clash threshold: Timed out waiting for board response" / "swing-on speed: Device disconnected while sending 'get_gesture swing_on'" — reuses the exact exception `.Message` values from the typed hierarchy in RESEARCH.md Pattern 1 verbatim; never re-wrap or genericize them |
| Panel banner retry button (per item) | "Retry" (icon-optional; if using an icon, `Icons.Material.Filled.Refresh`, matching MudBlazor convention elsewhere in the app) |
| Global toast (D-04, background load failure while on another page) | "Settings failed to load: {reason}" — reuses the exact existing `Snackbar.Add($"Failed to load settings: {ex.Message}", Severity.Error)` phrasing already used in `Settings.razor.cs`/`Dashboard.razor.cs` for consistency; do not invent new phrasing for what is functionally the same failure surfaced from a different trigger point |
| Empty state (all settings loaded successfully, nothing failed) | No banner is rendered at all — banner presence is conditional on `FailedSettings.Any()`. There is no "0 failures" empty-state copy needed; absence of the banner IS the empty state. |
| Unsupported setting (ERR-02, hidden case) | No copy — per D-02, unsupported settings render nothing at all (not even a placeholder row). This is a deliberate absence, not a state requiring copy. |
| Destructive confirmation | Not applicable — Phase 1 introduces no destructive actions (no deletes, no irreversible writes). The existing two-step delete-confirm pattern (`PresetsBar.razor.cs ConfirmDelete()`: click once → Snackbar warning "Click trash again to confirm deletion" → click again within 3s to confirm) is documented here only as the established precedent other phases should match; it is not invoked by any Phase 1 UI element. |

## Interaction Contract (Phase 1 specific — not in standard template, added because this phase is interaction-heavy)

| Interaction | Behavior |
|-------------|----------|
| Setting fails to load (genuine failure, not unsupported) | Row does NOT appear in its normal settings section; instead its label + reason appears in the panel-level error banner (D-01). No per-field inline error — this was explicitly excluded in REQUIREMENTS.md Out of Scope. |
| Setting is unsupported by firmware (D-02) | Row does not appear anywhere — no banner entry, no log-visible-to-user artifact, matches `/old` and today's behavior exactly. |
| User clicks "Retry" on one failed item | Only that single setting's load is retried (`FailedSetting.Retry` callback per RESEARCH.md Pattern 3) — the entire settings load sequence does NOT re-run. On success, the item is removed from `FailedSettings` and (if now loaded) appears in its normal section on next render via the existing `StateChanged` event. On repeat failure, the item stays in the banner with a possibly-updated reason string. |
| Background load fails while user is on a different page (D-04) | A `Severity.Error` Snackbar toast fires immediately, app-wide, via the `InvokeAsync`-wrapped event handler in the root layout component (RESEARCH.md Pattern 4/Pitfall 3). This does NOT replace the panel banner — if/when the user navigates to Settings afterward, the persistent banner is still shown for any settings that remain failed. |
| No automatic retry | Never — D-01 explicitly forbids background/automatic retry for any failed setting. Only an explicit user click triggers a re-attempt. |
